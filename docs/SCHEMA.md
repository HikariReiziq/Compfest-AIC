# Desain Skema Basis Data COBA

Dokumen ini menjelaskan **bagaimana baris dan kolom ditentukan**, bukan sekadar
mendaftar tabel. Setiap keputusan disertai alasan dan konsekuensinya.

---

## 1. Aturan pertama: apa yang layak masuk Postgres

Proposal menjanjikan satu hal yang langsung membentuk arsitektur data:

> Semua jawaban dan riwayat feedback hanya hidup selama sesi berjalan dan
> dihapus otomatis begitu sesi berakhir.

Janji itu ditegakkan lewat pemisahan tempat penyimpanan, bukan lewat pekerjaan
pembersihan berkala:

| Sifat data | Contoh | Tempat | Alasan |
|---|---|---|---|
| Durable, dibagi banyak pengguna | produk, kategori, size chart, aturan gaya | Postgres | Butuh integritas relasional dan query lintas baris |
| Ephemeral, milik satu sesi | hasil scan tubuh, jawaban kuesioner, riwayat feedback | Redis + TTL | Hilang sendiri saat sesi berakhir |
| Turunan, bisa dihitung ulang | hasil rekomendasi, size chart yang sudah dipivot | Redis (cache) | Boleh hilang tanpa kehilangan kebenaran |

Konsekuensi yang paling terasa: **tidak ada tabel `buyer` maupun `answer`.**
Jalur paling sibuk aplikasi ini, yaitu setiap kali pembeli menjawab satu
pertanyaan, tidak menyentuh Postgres sama sekali.

## 2. Menentukan baris: apa yang dihitung sebagai satu baris

Untuk tiap tabel, pertanyaannya selalu sama: *satu baris di sini mewakili apa?*

| Tabel | Satu baris = | Perkiraan volume |
|---|---|---|
| `product` | satu item katalog | ~44.000 |
| `category` | satu simpul hierarki | ~150 |
| `colour` | satu warna dasar beserta koordinat LAB-nya | ~50 |
| `undertone_palette` | kecocokan satu warna terhadap satu undertone | 4 x 50 = 200 |
| `style_rule` | satu aturan "atribut personal X mendorong target Y" | ratusan |
| `size_chart` | satu tabel ukuran untuk kombinasi kategori + gender + region | puluhan |
| `size_chart_entry` | **satu dimensi pada satu ukuran** | ribuan |
| `product_attribute` | satu label atribut pada satu produk | ratusan ribu |
| `asset_3d` | satu berkas aset untuk satu produk pada satu ukuran dan LOD | puluhan ribu |
| `recommendation_feedback_daily` | cacah suara pada satu irisan anonim per hari | tumbuh harian |

Butir yang paling menentukan ada di `size_chart_entry`, dan dijelaskan di
bagian 4.

## 3. Hierarki kategori: satu tabel rekursif, bukan tiga kolom teks

Dataset menyediakan tiga kolom: `masterCategory`, `subCategory`, `articleType`.
Cara paling gampang adalah menyalinnya jadi tiga kolom `varchar` di `product`.

Itu tidak dilakukan, karena:

1. **Data berulang.** "Apparel" akan tertulis puluhan ribu kali.
2. **Tidak ada yang menjaga konsistensi.** "Tshirts" dan "T-Shirts" bisa hidup
   berdampingan tanpa ada yang menghalangi.
3. **Menambah tingkat berarti mengubah skema.** Tingkat keempat berarti
   `ALTER TABLE` pada tabel puluhan ribu baris.

Yang dipakai: satu tabel `category` yang menunjuk ke dirinya sendiri lewat
`parent_id`, dengan kolom `level` menandai tingkat. Produk selalu menunjuk ke
simpul daun (`articleType`).

```
category(id, level, name, slug, parent_id, item_slot, is_active)
```

Konsekuensinya, filter "semua Apparel" butuh penelusuran ke bawah. Itu
diselesaikan dengan recursive CTE di [catalog.py](../app/services/catalog.py),
dan hasilnya di-cache. Alternatif materialized path ditolak karena butuh
pemeliharaan setiap kali hierarki berubah, sementara hierarki katalog ini
praktis statis.

Kolom `item_slot` hanya diisi pada level `article`. Kolom inilah yang membuat
sistem tahu satu outfit sudah lengkap atau belum.

## 4. Size chart: format panjang, bukan lebar

Ini keputusan paling penting di seluruh skema.

**Format lebar** (yang biasanya terpikir lebih dulu):

```
size_chart_entry(size_label, chest, waist, hip, inseam, shoulder, face_width, ...)
```

Bentuk ini gagal karena tiap jenis garmen memakai dimensi berbeda:

- kaos: lingkar dada + panjang badan
- celana: lingkar pinggang + panggul + inseam
- kacamata: lebar wajah

Hasilnya tabel penuh `NULL`, dan setiap jenis garmen baru menuntut `ALTER TABLE`.

**Format panjang** yang dipakai:

```
size_chart_entry(size_chart_id, size_label, sort_order, measurement_key_id, min_value, max_value)
```

Satu baris = satu dimensi pada satu ukuran. Skema berhenti berubah selamanya.
Dimensinya dijaga foreign key ke `measurement_key`, jadi tidak bisa salah ketik.

Harganya: membaca satu size chart utuh butuh operasi pivot. Harga itu dibayar
sekali lalu hasilnya disimpan di cache Redis per size chart. Karena satu chart
melayani ribuan produk, satu entri cache menutup sangat banyak permintaan.

Kolom `sort_order` ada karena tanpanya "L" akan terurut sebelum "M" secara
alfabet.

## 5. Menentukan tipe kolom

| Kebutuhan | Tipe yang dipakai | Alasan |
|---|---|---|
| Primary key tabel besar | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 8 byte, tidak akan habis, indeks padat |
| Primary key akun | `UUID` | ID muncul di URL; angka berurutan membocorkan jumlah dan urutan pendaftaran |
| Uang | `NUMERIC(12,2)` | `FLOAT` menghasilkan galat pembulatan yang tidak pernah bisa dibenarkan pada nilai uang |
| Dimensi tubuh | `NUMERIC(6,2)` | Presisi 0,01 cm sudah lebih halus dari ketelitian scan kamera |
| Skor kecocokan | `FLOAT` | Nilai perkiraan, presisi biner tidak masalah |
| Waktu | `TIMESTAMPTZ` | `TIMESTAMP` tanpa zona waktu selalu jadi bug saat deploy lintas zona |
| Himpunan nilai tertutup | `VARCHAR(32)` + `CHECK` | Lihat bagian 6 |
| Struktur bebas | `JSONB` | Pilihan jawaban kuesioner: dibaca utuh, tidak pernah jadi sasaran join |
| Pencarian teks | `TSVECTOR` kolom ter-generate | Dihitung Postgres, aplikasi tidak bisa lupa memperbaruinya |

### Kenapa bukan `ENUM` native Postgres

Menambah nilai ke `ENUM` native butuh `ALTER TYPE`, yang di beberapa versi
Postgres tidak bisa dijalankan di dalam blok transaksi bersama migrasi lain, dan
menghapus nilai praktis mustahil. `VARCHAR` + `CHECK` memberi jaminan integritas
yang sama sambil menyisakan jalan keluar berupa `ALTER ... DROP/ADD CONSTRAINT`
yang murah. SQLAlchemy menghasilkan bentuk ini lewat `native_enum=False`.

## 6. Aturan gaya: tiga foreign key eksklusif, bukan satu kolom polimorfik

`style_rule` perlu menunjuk ke sasaran yang bisa berupa kategori, atribut, atau
warna. Godaannya adalah membuat `target_type varchar` + `target_id bigint`.

Bentuk itu ditolak karena mematikan integritas referensial: kategori bisa
terhapus sambil meninggalkan aturan yang menunjuk ke ketiadaan, dan database
tidak punya cara mencegahnya.

Yang dipakai: tiga kolom foreign key nullable, dengan satu batasan yang
memastikan tepat satu di antaranya terisi.

```sql
CHECK (num_nonnulls(target_category_id, target_attribute_id, target_colour_id) = 1)
```

Postgres tetap menjaga relasi, dan aturan yang menggantung tidak mungkin ada.

## 7. Kolom yang menyiapkan tempat untuk AI

Model belum dipasang, tetapi tempatnya sudah disiapkan sekarang supaya tidak
perlu migrasi besar nanti:

| Kolom | Gunanya saat AI masuk |
|---|---|
| `product_attribute.source` | Membedakan label hasil model dari anotasi manusia |
| `product_attribute.model_version` | Menghapus keluaran model lama tanpa menyentuh anotasi manusia |
| `product_attribute.confidence` | Menyaring label berkeyakinan rendah saat menilai |
| `style_rule.source` | `stylist` untuk kurasi manusia, `learned` untuk hasil belajar mesin |
| `style_rule.is_active` | Mematikan aturan yang ternyata buruk tanpa deploy ulang |
| `style_rule.rationale` | Alasan yang ditampilkan ke pembeli |
| `recommendation_feedback_daily` | Sinyal pelatihan lintas sesi, sepenuhnya anonim |

Aturan hasil belajar mesin dan aturan dari stylist hidup **di tabel yang sama**,
sehingga keduanya bisa dibandingkan langsung dan dimatikan satu per satu.

### Tahap berikutnya: pencarian berbasis embedding

Saat retrieval multimodal dibutuhkan, tambahkan ekstensi `pgvector` dan tabel:

```sql
CREATE TABLE product_embedding (
    product_id     BIGINT REFERENCES product(id) ON DELETE CASCADE,
    model_version  VARCHAR(48) NOT NULL,
    embedding      vector(512) NOT NULL,
    PRIMARY KEY (product_id, model_version)
);
CREATE INDEX ON product_embedding USING hnsw (embedding vector_cosine_ops);
```

Sengaja belum dibuat sekarang: menambah ekstensi yang belum terpakai hanya
menambah hal yang harus dipasang di setiap lingkungan.

## 8. Indeks: mengikuti query, bukan menebak

Indeks hanya dibuat untuk pola query yang benar-benar ada. Setiap indeks
memperlambat penulisan dan memakan tempat, jadi indeks tanpa pembaca adalah
kerugian bersih.

| Indeks | Melayani |
|---|---|
| `ix_product_reco_filter (gender, usage_context, category_id) WHERE is_active` | Filter utama mesin rekomendasi. Parsial, jadi produk nonaktif tidak ikut membebani |
| `ix_product_keyset (popularity_score, id)` | Keyset pagination dan urutan peringkat |
| `ix_product_search` GIN pada `search_vector` | Pencarian nama produk |
| `uq_product.external_id` | Impor ulang dataset yang idempoten |
| `ix_size_chart_entry_chart (size_chart_id, sort_order)` | Memuat satu chart utuh dalam satu pemindaian |
| `ix_style_rule_subject (subject, subject_value, is_active)` | Memuat aturan untuk satu atribut personal |
| `uq_feedback_slice` (NULLS NOT DISTINCT) | Upsert agregat feedback |

Urutan kolom pada indeks komposit mengikuti selektivitas dan pola filter:
`gender` hampir selalu ada di setiap query rekomendasi, `usage_context`
menyusul, `category_id` paling jarang berdiri sendiri.

### Kenapa keyset, bukan `OFFSET`

`OFFSET 10000` memaksa Postgres membaca lalu membuang 10.000 baris. Pada katalog
44.000 produk, halaman terakhir jadi jauh lebih lambat daripada halaman pertama.
Cursor berbasis nilai kolom terakhir (`popularity_score`, `id`) membuat biaya
setiap halaman sama, dan bonusnya: baris tidak akan terlewat atau tampil dua
kali saat katalog berubah di tengah penelusuran.

## 9. Privasi sebagai bentuk skema

`recommendation_feedback_daily` adalah satu-satunya tempat feedback bertahan
melewati sesi. Yang disimpan hanya:

```
(hari, produk, bentuk_tubuh, undertone, occasion) -> impressions, likes, dislikes
```

Tidak ada session id, user id, alamat IP, maupun sidik jari perangkat. Satu baris
mewakili banyak orang sekaligus, sehingga tidak bisa dikembalikan ke individu.
Inilah yang memungkinkan rekomendasi membaik lintas sesi tanpa melanggar janji
di proposal. Perilaku ini bisa dimatikan lewat `FEEDBACK_AGGREGATE_ENABLED=false`.
